## Method

- Endpoint inventory built from the real composition-root sources of
  truth: `src/infra/config/routes.ts`, `src/infra/http/routes/*.routes.ts`,
  and the served `GET /docs.json` document (assembled from
  `src/infra/docs/*.swagger.ts`). No route was assumed; each row below is
  traceable to a `router.<method>(...)` registration.
- Endpoints were exercised against `createApp()` (the real composition
  root) using `supertest`, with the same non-production harness the
  existing E2E suite already uses: `mongodb-memory-server`, started/torn
  down via `test/e2e/setup/mongo-memory-server.global-setup.ts` /
  `global-teardown.ts`, wired through `test/jest-e2e.json`
  (`MONGO_URI` is generated by the in-memory server, not read from a real
  environment).
- `JWT_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `JWT_EXPIRES_IN`, and
  `JWT_REFRESH_EXPIRES_IN` were set in-process to disposable, non-real
  placeholder values for the duration of the run, following the exact
  pattern already used in `test/e2e/app.e2e-spec.ts`. No `.env` file was
  read or inspected as part of this task, and no credential value appears
  anywhere in this report.
- Cloudinary credentials come from whatever local environment configures
  `createApp()`'s `CloudinaryStorageService`; this task deliberately did
  **not** invoke a real Cloudinary upload/delete call (see the Upload
  section below) to avoid any risk of touching a non-isolated or
  production-equivalent Cloudinary account, since that could not be
  confirmed without reading `.env` (which this task must not do).
- A temporary, disposable diagnostic script (`supertest` + the harness
  above) was used to exercise every endpoint in dependency order. It was
  deleted after evidence was collected; it is not part of the delivered
  changes and is not a substitute for the permanent E2E suite gap noted
  below (see "E2E Coverage Comparison").
- No production environment, production database, or production
  credentials were used at any point (FR-007, NFR-002).

### Stateful flow verification (FR-005, AC-005)

The following flows were run **in dependency order**, not as isolated
calls:

1. `POST /auth/login` → `GET /auth/session` (Bearer from login) →
   `POST /auth/refresh` (using login's cookies, CSRF header omitted then
   included) → `POST /auth/logout` (using refresh's rotated cookies).
2. `POST /works` (using login's Bearer token) → `GET /works` (confirms
   the created work is publicly listed) → `POST /works/:workId/comments`
   → `GET /works/:workId/comments` (confirms pending comment excluded) →
   `PATCH /admin/comments/:id/approve` → `GET /works/:workId/comments`
   (confirms now-approved comment included) → `PATCH /admin/comments/:id`
   → `DELETE /admin/comments/:id` → `DELETE /admin/works/:workId`.
